# 舰队科技列表

扫描中的图像省略号必须紧邻名称正文；短名右侧空白中的卡面亮点不能把普通舰误判为截断的特殊版本。

## 页面与资料

入口是「舰队管理 → 数据分析 → 舰船科技分析」，路由 `/i/:instance/task/FleetAnalysis?tab=technology`。旧 `/i/:instance/task/FleetTechnology` 自动跳转。页面布局与蓝色表头参考[碧蓝航线 Wiki](https://wiki.biligame.com/blhx/舰队科技)，支持组合筛选、搜索、排序、每页 50 条、固定表头和窄屏横向滚动。阵营/分组额外提供基于资料的 μ 兵装、小型舰筛选，不改变舰船实际阵营。

默认及重新载入时显示「合并记录」。两个视图均保留完整图鉴，只切换舰船状态与科技计算的来源：

- 「舰船底账」：获取、满星、120 级、等级、科技点和舰船属性加成只使用服务端 `ships[].ledger` 的已确认底账投影；未获取为完整目录减去底账已获取舰船。底账为空时仍可选择，全部舰船均未获取。
- 「合并记录」：**已获取 = 底账已确认获取 ∪ 人工已确认获取；未获取 = 完整目录 − 已获取并集。** 同一舰船组只计算一次，满星和 120 级进度也分别取两来源的正向并集，合并等级取两来源有效等级的最大值。人工的否定、空值或低等级只作用于人工来源，不撤销底账已经确认的正向证据。

所有筛选、着色、等级、完成数、已确认科技点和舰船加成均跟随当前视图；没有人工正向证据时，两视图的结果一致。阵营科技等级是独立的共享设置，两视图使用相同的已录入阵营加成。待核对项单列，不参与任何视图的舰船进度。

累计科技等级仍保存在数据库中，不因退役副本或人工编辑而删除；它不作为底账与人工之外的第三份获取来源。两来源都没有获取证据的舰船保留在目录中，状态为未获取。清除人工记录后仍保留底账贡献；底账没有的舰船则回到未获取。编辑不改写当前舰船底账，旧 JSON 不作为报告来源。

界面示例：[合并记录](images/fleet-technology-scan-history.png)、[底账视图](images/fleet-technology-scan-latest.png)。两视图均展示完整目录，科技计算分别基于两来源并集或已确认底账。

静态资料离线打包。`assets/ship/fleet_tech.json` 按 Lua `ship_data_group.group_type` 保存可见图鉴、编号、方案分类、三阶段科技点、获得与 120 级加成及四大阵营升级加成；名称、稀有度和类型关联现有 `ship_data.json`。来源提交和日期来自本地 Lua Git 快照，不代表已实时同步游戏服务器。全部、有科技、无科技均可显示；无科技的数值列显示破折号。

## 个人记录与状态

舰船数据保存在每个实例独立的 `config/fleet/<实例名>.sqlite3`。当前卡片保存在类型化舰船表中，最新扫描信息只有一条；累计科技进度、科技人工字段、阵营等级和心智设置独立存储。以下是报告的数据投影，不是历史扫描表：

- `observed`：以群组 ID 为键保存扫描到的最高历史等级，只增不减。
- `current`：保留旧累计兼容投影，不作为新增的获取来源。
- `absent`：旧扫描缺失信息，仅供兼容和诊断。
- `ledger_levels`：仅从当前已确认底账派生的群组与等级；不混入待确认扫描和旧累计记录。
- `manual`：每个群组独立的人工获取、满星、Lv.120 和等级；明确未获取时，人工来源整体关闭，遗留等级不参与并集。
- `manual.<群组>.level_toggle`：单击完成的低/高等级端点，刷新、重进或重启后仍可恢复原等级。
- `nations`：四大阵营手工录入的科技等级，空值为未知，0 为确认未升级。
- `last_scan`：等级范围、到底状态、数量核验、群组/等级清单和稳定摘要。
- `review_ships`：未确认的卡片与候选群组，不作为获得证据写入。

没有有效获取证据的舰船显示为未获取，可在完整列表中筛选。着色与 Wiki 一致：未获取不标色，已获取但未到 120 级只标绿“解锁”格，达到 120 级后整行标绿，125 同样达标。零科技舰船也保留获取与等级状态，只有点数和加成为空。各来源有效等级大于 100 时默认满星；任一来源确认满星即计入，仍未知的满星不计点数。底账视图按底账等级计算，不借用人工或历史等级。

编辑模式的勾选和等级输入只编辑人工来源，行底色始终表示最终并集结果。人工获得、完成、满星可独立增减；人工等级输入显示人工值，未录入保持空白。完成切换只使用人工端点：人工 105 级在 105/120 间切换，人工 125 级保留 125 端点；底账的高等级不会被复制成独立人工证据。取消人工获得后其遗留等级不参与计算；清除人工记录不会撤销底账已有进度。保存失败保留草稿与重试提示，合并计算以服务端确认结果为准。


失败保留浏览器草稿和提示，自动刷新不能推进待提交草稿的版本；冲突时主动重载最新记录后再提交。编辑模式使用合并视图，只修改独立人工证据。总属性按当前视图累积已确认获得/120 加成，再加入两视图共用的已录入阵营等级；阵营表的 add 已是该等级累计值，只加入选中等级一次，导驱/风帆子类不重复累计。

## 扫描与兼容

统一工具 `DockScan` 使用 `DockScan.Dock.MinLevel/MaxLevel`，默认 1–125（含边界），满足 `1 ≤ 最低 ≤ 最高 ≤ 125`。原始物理副本逐艘保存在 SQLite 当前舰船表中，同名副本也分别保存。每张卡片有内部记录 ID，不代表游戏永久身份；新读取只产生待确认差异，玩家采纳后才更新当前清单；明确对应的更新保留内部 ID，只有新增记录分配新 ID。科技与心智同时读取已确认底账。旧任务名保留为共享扫描的薄兼容入口，工具菜单不再展示。

数据分析页面经 `dock.configure` 保存范围，再经 `tasks.run(DockScan)` 显式启动；浏览页面和切换分析不会启动游戏。科技服务从当前底账与人工记录派生报告；数据库独立保存人工覆盖与阵营等级，新人工编辑不复制底账，也不改写实例 JSON。完整性证明及旧数据兼容见 [船坞数据分析](fleet-analysis.md)。

科技扫描复用页面稳定、三排行进及滚动配准，使用自己的可见图鉴群组目录与合并方式，不套用心智按名称合并或计费排除。当前舰船表逐卡保存可靠的名字和等级；科技投影按群组取本轮最高等级。局部读取只建议已读到记录的新增或更新，未读到的卡片不删除，所有差异均等待采纳。累计科技保留既有最高等级。改造用实际改造名关联原群组，II、META、小型和兵装保持独立。飞机、战列字形提供正向舰种证据，使同名加贺、天城分别保存；同名同舰种不能凭稀有度、排序或全收藏假设选人，候选在页面供手工确认。

共享扫描器对一个阈值边界行内的抗锯齿像素进行二维八邻接核验，前后行仍采用严格颜色，首尾端点不扩张，不修改通用 `Scroll` 阈值。圆角采样不依赖固定横向跨度。暂时无法识别滑块只使该帧失去底部证明；卡片有独立唯一位移证据时可以继续范围扫描，不能据遮挡或静止误报到底。

严格滑块仅差轨道终点两行时，另行核对逐行收窄、八邻接且延伸至终点的圆角端帽颜色；
该正向证据仅用于底部退出，不修改滑块端点和位移标定。末页不必对齐三排目标，只读取完整可见行。
科技与心智从共享底账分别投影，不再主动同步心智人工清单；同名身份必须依靠确认的群组。

同名同等级的重复卡片可能在相差整行的多个位移上同分，整行移动甚至看起来没有变化。滑块两个端点同向移动、已核实的按住结束手势边界及此前明确位移的比例校准可进一步约束候选；仍须得到唯一图像匹配，不直接采用触控距离。无独立证据的重复画面不能当作零位移，当前步最多三次新帧复核，无法确认时保留旧结果退出。
小距离按住拖动的物理幅度小于半排行距时，可以使用包含零和反向候选的对称界限核验；滑块亚像素移动不可见也不直接中断，仍须图像在界限内唯一匹配。

卡片缺格在当前页最多重读三次；有可靠行位及同排其他卡片证据时，只把缺失卡位保留为未知等级待核对，其余舰船继续处理。整个页面无法确认时不凭网格捏造舰船。等级、编队或排序疑点仅作用于原卡位及必要交界；之后完整可靠的普通舰页面可恢复早停，历史单点疑问不强制扫到底。待核对项仍保留，当前页存在疑点、缺格或未越过等级下限时不能早停。

改造别名同时读取 Lua 的 `sharecfg` 与 `sharecfgdata` 皮肤表，以真实群组关联；不连续的改造编号也不能被误当作剧情条目丢弃。改造后舰种采用同组实际改造类型（例如战列改航战）核对。小型分组采用资料标记及同阵营同舰种的“小＋原舰名”关系，普通舰名中的“小”不作为排除条件。`MET…`、μ 标记与唯一名称的截断后缀保留身份含义；II 家族要求多次明确后缀。失败字图只做有界笔画复读，两种处理独立确认相同群组后采用，不添加特定舰名替换表。

扫描前经主界面重新进入船坞，清空隐藏搜索词，再确认搜索关闭、重置收藏与筛选并确认顶部；仅收起搜索框不能证明关键词已清空。非底部页必须完整三排七列。核实新页并新增物理船位后重新计量滚动期限，有界 OCR 复读不占用下一段滚动期限；重复旧船位不能续期。仅 **1–125、无过滤、到达底部、物理卡片数与船坞数量一致且无未确认条目** 时更新缺失状态。局部范围、OCR 疑点、页面缺格或未到底不能撤回累计科技成就；成功读取只提交待采纳差异。取消或异常不提交，保留上次当前清单。扫描中途不提交，成功后将建议更新放入待确认区，未采纳前不改变人工底账。新舰船无证据时默认未获得，既有历史和人工记录不因资料生成而删除。

旧任务数据默认忽略。用户主动读取当前实例本地 JSON 后，仅生成舰船、科技和阵营等级差异，不上传、不清理原文件。用户可在舰船数据标签逐条或全部采纳、忽略；未采纳前，科技列表与所有人工状态保持数据库中的已确认值。后续交互只使用 SQLite。

备份与恢复前停止应用，再复制对应 SQLite 文件；仅备份任务配置不会包含舰船数据。


自动扫描当前支持国服，其他游戏服仍可手工记录。`cache/fleet-tech-scan-diagnostics` 标志保留全部页原帧和卡位诊断，用于离线复核；不减弱排序、位移或页完整性校验。

## API

| 方法 | 行为 |
| --- | --- |
| `fleetTech.catalog(instance)` | 只读离线目录与来源版本 |
| `fleetTech.report(instance)` | 只读实例状态、范围、点数与加成 |
| `fleetTech.patch(instance, revision, changes, nations)` | 事务编辑人工覆盖/阵营等级；快捷变更使用 `toggle` 与绝对 `target`，版本冲突拒绝写入 |
| `fleetTech.syncMind(instance)` | 只读返回科技报告，不导入心智清单 |

人工编辑接口标记 `mutates=True`，沿用认证与演示模式写保护；旧同步接口为只读。状态字段仍禁止通过普通 `config.patch` 整体替换。

## 生成与更新

使用同一 Lua 快照分别运行：

```powershell
uv run python -m dev_tools.ship_data_extractor --lua-repo <Lua仓库路径>
uv run python -m dev_tools.ship_data_extractor --lua-repo <Lua仓库路径> --names-only
uv run python -m dev_tools.ship_data_extractor --lua-repo <Lua仓库路径> --fleet-tech-only
```

校验图鉴与科技的群组关联、编号唯一性、非空名称、完整字段及点数汇总。目录在进程内缓存，部署资料后由应用更新重启加载。更新 fork 的上游方式与本机路径只记在被 Git 忽略的本地技能，本文不复制本机路径。
